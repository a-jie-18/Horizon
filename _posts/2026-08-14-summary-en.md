### [Spaghettifying DRAM: New Attack on AMD Jaguar](https://github.com/xoreaxeaxeax/skitter-creek-bath-salts) ⭐️ 8.0/10

Security researcher Christopher Domas has released a new DRAM attack technique called &\#x27;Spaghettifying DRAM&\#x27;, demonstrated on the AMD Jaguar architecture \(AMD16h, circa 2013\). The attack exploits the memory controller&\#x27;s register interface to gain ring-0 privileges and access hidden system resources, effectively bypassing security boundaries. The README notes that Zen 3 has a different base address for memory controller registers, but it is unclear which newer CPUs are affected. The technique is significant because it exposes a hardware-level vulnerability that could undermine system security, though its immediate practical impact is limited to older hardware.

hackernews · matt\_d · Aug 13, 14:17 · [Discussion](https://news.ycombinator.com/item?id=49286341)

**「Background」** Row hammer is a DRAM vulnerability first publicly documented in 2014, where repeatedly accessing \(hammering\) a row of memory cells can cause bit flips in adjacent rows due to electrical interference. This attack exploits the physical properties of DRAM to corrupt data, potentially leading to privilege escalation or other security breaches. The &\#x27;Spaghettifying DRAM&\#x27; technique, presented by security researcher Christopher Domas, extends this concept by manipulating the memory controller&\#x27;s configuration registers to remap physical addresses, effectively &\#x27;spaghettifying&\#x27; the memory layout and enabling more effective row hammer attacks. This work targets AMD Jaguar, a low-power architecture from 2013, and highlights the broader attack surface in modern DRAM controllers.

**「Impact」** On affected systems \(AMD Jaguar\), an attacker with ring-0 access can gain full control over hidden hardware features, potentially compromising system integrity. The impact on newer CPUs is uncertain, but the technique highlights a broader attack surface in DRAM controllers that may affect other processor families.

**「Community Discussion」** Commenters express enthusiasm for Domas&\#x27;s upcoming Black Hat talk, praising his ability to explain complex reverse engineering topics. Some note that the attack targets older hardware, questioning its relevance to modern CPUs, while others point out that the complexity of modern DRAM controllers creates a large attack surface. There is also speculation that console security teams \(Xbox, PlayStation\) might be concerned about similar vulnerabilities.

### [How Compaction Works in Pi](https://earendil.com/posts/compaction-in-pi/) ⭐️ 7.0/10

The article explains the technical implementation of context compaction in the Pi LLM, detailing how the model summarizes conversation history to manage context window limits. It highlights the trade-offs between preserving full history and maintaining performance, noting that compaction can lose intent and nuance. The discussion also covers alternative strategies like pruning low-value messages and using dual KV caches to summarize tokens during generation. The author emphasizes that compaction is a practical necessity for long conversations but suggests that keeping context small is often more effective.

hackernews · tosh · Aug 13, 17:57 · [Discussion](https://news.ycombinator.com/item?id=49289654)

**「Background」** Large language models have a fixed context window, which limits how much conversation history they can process at once. Context compaction is a technique where the model summarizes earlier parts of the conversation to free up space, allowing longer interactions without exceeding the window. This is distinct from pruning, which removes low-value messages entirely, and from prompt caching, which stores previous computations to reduce cost.

**「Impact」** Developers using Pi or similar LLMs in agentic workflows will need to balance compaction against history preservation, as summarized conversations can lead to less accurate future responses. The community suggests that staying below 30% context utilization and using branching or dual KV caches can reduce the need for compaction, but these methods may increase complexity or cost.

**「Community Discussion」** Commenters debate the merits of pruning versus compaction, with some preferring to keep full history to avoid losing intent. Others propose technical workarounds like dual KV caches to summarize during generation, while noting that prompt caching costs discourage creative compaction techniques. A common consensus is that avoiding compaction altogether by keeping context small is often the best strategy.

### [systemd-journald Log Line Causes Excessive Disk Writes](https://github.com/systemd/systemd/issues/40262) ⭐️ 7.0/10

A GitHub issue \(systemd/systemd\#40262\) reports that a single log line can cause 49KB+ of disk writes on ext4 and 110KB+ on btrfs in systemd-journald. This highlights a significant performance and design flaw in the widely used logging system, as the journal format appends data and updates metadata, leading to disproportionate write amplification. The issue has sparked community debate about journald&\#x27;s design intent and practical limitations, particularly regarding filtering and storage efficiency. The report is important for system administrators and developers relying on journald, though it does not represent a paradigm shift.

hackernews · ValdikSS · Aug 13, 18:41 · [Discussion](https://news.ycombinator.com/item?id=49290215)

**「Background」** systemd-journald is the logging daemon in systemd-based Linux distributions, storing logs in a binary journal format. The format is designed for robustness and atomicity, appending data at the end of files and updating headers, which can cause write amplification when small log entries trigger larger metadata updates. This design was intended to ensure reliability but has trade-offs in disk usage and performance.

**「Impact」** Users of systemd-journald on ext4 or btrfs filesystems may experience excessive disk I/O and storage consumption, especially on systems with high log volume, potentially degrading performance and wearing out SSDs. The lack of granular filtering options exacerbates the issue, as administrators cannot easily suppress chatty subsystems without external tools like rsyslog.

**「Community Discussion」** Community comments criticize journald for allowing applications to log excessively without restraint, and note that the original design intent did not anticipate such write amplification. Users also point out that filtering is practically limited to severity levels or non-persistent storage, making it difficult to manage verbose logs from drivers or desktop components.
